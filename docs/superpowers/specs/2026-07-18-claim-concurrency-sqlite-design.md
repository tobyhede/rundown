# Claim Concurrency: SQLite State Store with Transactional Generation-CAS

**Status:** Design spec, implementation-ready (architecture); implementation is phased — see Scope & Phasing.
**Issue:** #608 (claim resolve-and-commit race), and the broader lock-structure problem it exposed.
**Supersedes:**
- The earlier 2026-07-17 SessionLock-guard working plan; that partial approach is rejected below.
- The JSON fencing-token design previously held in this file (see git history) — rejected; it re-implements transactions by hand (see Rejected Alternatives).

## Goal

Close the #608 check-then-act claim race, including its cross-run parent-liveness dimension, by replacing the hand-rolled multi-file state-coordination scheme with a single embedded SQLite database. The decisive state write of a claim-authorized mutation re-validates the complete claim predicate atomically with that write; effectful commands additionally use the execution protocol below around their out-of-transaction effects. This removes the four domain-lock rank, its ABBA hazards, and the `*Unlocked` twin methods. It does not eliminate synchronization or make arbitrary shell effects transactional: `file-lock.ts` remains for its independent consumers and the sql.js persistence cycle, and DB-row execution ownership remains explicit.

## Context and Rationale

### The root problem is the lock structure

Rundown coordinates multiple OS processes (an orchestrator `rundown`, delegated child `rundown` processes, per-step shells) mutating shared `.rundown/` state via four hand-rolled file mutexes in a fixed acquire-order ("rank"): `DelegationLock → SessionLock → CompletionLock → RunStateLock`. This is hand-composed multi-resource two-phase locking without a lock manager or transactions. Every hard symptom traces to it: #608 (check-then-act across two lock domains), the ABBA traps and `*Unlocked` twin-method sprawl (incremental acquisition + non-reentrancy), `collect` being inexpressible under a guard (its propagation reaches `DelegationLock` and a CLI callable), and the RD-810 hold-time cascades (a project-global `SessionLock` that must not be held across slow work).

### Rejected repair approaches

1. **SessionLock-outer guard** (2026-07-17 plan): implementable but fragile — guards only the single decisive mutation, defers `collect` / run-control cascade / explicit-target `pass`/`fail`, and rests on per-path rank reasoning (its own first draft shipped five blocking defects).
2. **Collapse claim authority onto per-run `RunStateLock`**: fatal — the decisive mutation re-acquires `RunStateLock(sameId)` (non-reentrant → 5s timeout) and takes `CompletionLock` while holding `RunStateLock` (rank inversion); and delegated-claim validity is cross-run (parent liveness), which a per-run lock cannot serialize.
3. **Fencing-token / version-CAS over the JSON files**: the right *concept*, wrong *substrate*. A review found four criticals: claim (session) and generation (run state) can't be bumped atomically across two files; treating a missing field as generation-zero violates the no-migration rule; `delegate` and `collect` are multi-write workflows, not single-CAS consumers. All four are symptoms of re-implementing transactions by hand. An embedded transaction removes them.

### The canonical fix

External research (July 2026) shows every mature claim/lease system converges on one principle: **do not hold a database transaction across resolve→act; make the resource re-validate ownership atomically in the mutation that records the result.** Temporal Activity task tokens, BullMQ job-lock tokens, Solid Queue claimed-execution rows, GoodJob/Oban queue claims, Kubernetes `resourceVersion`, and Postgres `SELECT … FOR UPDATE SKIP LOCKED` all establish one active owner and reject stale state transitions. Rundown's claim is a bearer token — the textbook optimistic case. SQLite provides the atomic transaction that makes the CAS sound; the JSON version could not.

The same prior art establishes an equally important boundary: **an ownership lease does not provide exactly-once external effects.** Temporal and BullMQ explicitly accept repeat execution and require idempotency; GoodJob and Oban reclaim/retry interrupted work; Solid Queue instead marks orphaned claimed work failed for inspection. Kubernetes' own leader-election package explicitly says a lease alone is not fencing. If a worker completes an external effect and dies before recording completion, the database cannot distinguish that history from dying before or during the effect. Rundown therefore uses the row lease to prevent simultaneous recognized execution and stale DB commits, but fails closed to `recovery_required` when a dead owner may have started an arbitrary shell effect. It does not automatically re-execute ambiguous effects.

Primary prior art for this boundary:

- [Temporal Activity idempotency](https://docs.temporal.io/activity-definition#idempotency): an Activity may complete externally and execute again if its worker dies before reporting completion.
- [BullMQ manual fetching](https://docs.bullmq.io/patterns/manually-fetching-jobs) and [at-least-once warning](https://docs.bullmq.io/bull/important-notes): ownership tokens guard completion and renewal, while stalled recovery may double-process a job.
- [Solid Queue claimed executions](https://github.com/rails/solid_queue/blob/main/app/models/solid_queue/claimed_execution.rb) and [process-death behavior](https://github.com/rails/solid_queue#threads-processes-and-signals): relational ownership rows; orphaned in-flight work becomes an inspectable failure.
- [GoodJob interruption semantics](https://github.com/bensheldon/good_job/blob/main/README.md#interrupts-graceful-shutdown-and-sigkill) and [Oban Lifeline](https://hexdocs.pm/oban/Oban.Pro.Plugins.Lifeline.html): interrupted work may be retried or deliberately discarded depending on duplicate-effect risk.
- [Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/) and [client-go leader-election contract](https://pkg.go.dev/k8s.io/client-go/tools/leaderelection): lease ownership uses optimistic concurrency but does not itself guarantee fencing.
- [PostgreSQL queue locking](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE) and [SQLite transactions](https://www.sqlite.org/lang_transaction.html): `SKIP LOCKED` is a short-transaction queue-claim primitive; SQLite instead has one writer and uses `BEGIN IMMEDIATE` plus conditional updates.

Peer tools confirm the substrate choice: for mutable structured state with cross-record invariants, the 2026 canonical store is embedded SQLite (WAL + `busy_timeout` + `BEGIN IMMEDIATE`); tools that started on files-plus-locks and outgrew it (pnpm's index, Nix, OpenClaw) moved that state into SQLite. Rundown's current design is literally Yarn Berry's `lockPromise` + Cargo's ranked locks — a recognized pattern at its known ceiling.

### Empirical findings (WebContainer)

The docs `site/` runs the real CLI and its real state layer inside StackBlitz WebContainer (single-process; nested spawn is broken, so the #608 race never occurs there). SQLite viability in WebContainer was settled empirically via a Playwright/Chromium probe of the real WebContainer runtime:

- **Native SQLite is barred.** WebContainer's Node is v22.22.3; `require('node:sqlite')` returns a stub (constructed `DatabaseSync` instances have no prototype methods — the native C internals are omitted from the WASM Node build). Native addons (`better-sqlite3`) are blocked (`--no-addons`, no compiler). The hard constraint is precise: **WebContainer executes only JS and WASM; no native machine code.** No Node upgrade changes this — the blocker is native-in-WASM, not the version.
- **WASM SQLite works.** WebContainer's Node runs user WebAssembly (`WebAssembly.instantiate` of a hand-built module returned the right result), `npm install sql.js` succeeds, and sql.js (SQLite compiled to WASM) ran `CREATE`/`INSERT`/`SELECT` correctly.
- **sql.js persists across the demo's process model.** Three separate sequential `node` processes sharing the WebContainer FS — process 1 created a DB and exported it to a file, process 2 loaded and appended, process 3 loaded and read — returned the expected aggregate. The demo runs each `rundown` command as a separate process sharing the FS; sql.js with load-on-open / export-on-write satisfies that, single-process.

Conclusion: **SQLite is viable everywhere** — natively on real machines, and via sql.js (WASM) in WebContainer. WebContainer is not a blocker.

## Architecture

### One database replaces the JSON files and the locks

A single SQLite database (e.g. `.rundown/rundown.db`) holds all mutually-coordinated state currently spread across `session.json`, `runs/*.json`, and coordinated by the four locks: run state, claims, the stash slot, the default stack, and resolved completions.

**Deleted by this change:** `run-state-lock.ts`, `session-lock.ts`, `completion-lock.ts`, `delegation-lock.ts`, the four-lock rank, and every `*Locked` / `*Unlocked` twin-method pair that exists only to work around non-reentrancy. **Retained and reused:** `file-lock.ts` remains load-bearing for artifact-manifest writes and supplies the sql.js adapter's cross-process critical-section lock; its conservative process-liveness conventions are also reused by the DB execution-lease service, but the DB row—not a lock file—is the per-run ownership record. This migration replaces a four-lock *rank* with one uniform ownership protocol and moves authoritative state coordination into transactions; it does not eliminate synchronization outright.

**Authoritative mutable state lives in the DB — no mutable sidecar files.** The XState `snapshot` is part of authoritative run state; storing it in a mutable external file would recreate the cross-store atomicity problem this design eliminates. The architecture requires one of exactly two treatments for every piece of state, and forbids a mutable third:

- **Authoritative mutable state → SQLite columns.** The `snapshot`, run fields, claims, stash, stack, and completions are DB columns/rows, written inside the same transaction as everything else. This is the default and the recommendation for the `snapshot`.
- **Large immutable blobs → content-addressed FS, referenced transactionally.** Artifact outputs and the frozen `runbookSrc` are immutable once written; they may live as content-addressed FS files written *before* the DB commit, with the DB storing only the reference, committed transactionally. Orphaned blobs (written, commit lost) are reclaimed by an explicit prune, never read as authority.

Whether the `snapshot` is small enough to keep inline (recommended) or must be content-addressed is a size question the schema pass answers — but it must be one of these two models, never a mutable sidecar.

### Driver seam (capability-selected)

State access goes through one narrow, injectable `StorageAdapter`/store interface with two adapters. `transaction()` is the sole authoritative write path; callers cannot obtain a raw writable connection. Both adapters execute the **same SQL against the same schema**; the seam is a thin driver boundary (prepare/exec/transaction + persist), not two persistence models. The interface exposes an explicit capability value such as `multiProcess: true | false`, so unsupported adapter/runtime combinations are rejected by a checked branch rather than convention. The narrow seam replaces the current lock DI interfaces so unit tests can use structural store fakes without constructing real SQLite databases. No native addons are used anywhere (built-in `node:sqlite` + WASM `sql.js`). The repo already requires Node ≥ 24, so the native adapter's SQLite API is available with no engines change.

- **Native adapter — `node:sqlite`** (real machines, multi-process). WAL mode, `busy_timeout`, `BEGIN IMMEDIATE` for every writing transaction, short transactions, retry on `SQLITE_BUSY`. Provides genuine multi-process serialization — the property the file locks hand-rolled.
- **WASM adapter — `sql.js`** (WebContainer, single-writer only). In-memory database, loaded from the DB file on open. **sql.js provides *no* cross-process serialization** — `COMMIT` mutates only the private in-memory image, and two processes that each load, mutate, and export would clobber one another. The adapter therefore holds an adapter-owned advisory **lock file** around each short `load → transaction → export → replace` critical section. It MUST release that lock during effectful computation; holding it for an entire command would recreate RD-810 and globally serialize unrelated effects. The exported lease row makes later short transactions observe ownership; the file lock is what makes each load/CAS/export operation atomic across processes. Durability inside the lock is mandatory: export to a same-directory temp file, `fsync` the file, atomically rename it over the DB, `fsync` the containing directory where the host supports it, and only then report success; reclaim orphaned temp files on startup. Because `file-lock.ts` is non-reentrant, the adapter also owns one in-process async mutex/reentrancy boundary and never recursively acquires its file lock. A host broker that provides the same serialization may replace the file lock.

**Adapter selection is positive, not fallback.** Step 1 must name and test the concrete StackBlitz/WebContainer runtime marker used for positive identification; native-SQLite failure is never itself that signal. The selector chooses `sql.js` only when that marker identifies the supported single-writer WebContainer environment and chooses the native adapter otherwise. A multi-process runtime without working native SQLite is a hard startup error, not a silent downgrade.

### Concurrency model: versions, dependency validity, and computation

Two distinct monotonic counters are required — conflating them is unsound:

- **`claim_generation`** (claim validity) lives on `runs`, not on individual claim rows. It is bumped by every write that can change claim resolution. Claims retain the generation at which they were issued only as immutable issuance metadata; commit validity compares the captured value with `runs.claim_generation` and separately checks that the presented claim/tombstone is still active for that generation. Claim/stash triggers structurally bump the controlled run. When a parent becomes terminal, that transaction updates each linked child's claim/linkage row and **the same structural trigger owns the resulting child-generation bump**; the parent-terminal code does not also increment it directly. A valid holder's ordinary state mutation does not bump it. Mismatch at acquire or commit → `claim_superseded`.
- **`state_version`** (lost-update prevention). Bumped by *every* state mutation, including a valid holder's. Captured at read; a mismatch at commit means another writer advanced the run in between → `concurrent_modification`. Without this, two co-bearers of one claim could load the same state, compute conflicting snapshots, and sequentially overwrite each other — `claim_generation` alone (which valid mutations don't move) cannot catch this.

Execution ownership may also retain a monotonic diagnostic/future-fencing value:

- **`exec_epoch`** (execution-attempt ordering). Incremented on every successful acquisition and never reused. The random `exec_token` already supplies ABA-safe acquisition identity; the epoch is not required for internal correctness, but is retained for ordered diagnostics and possible downstream fencing. It only fences an external resource if that resource receives and enforces it. `runs` references the active attempt and stores its PID, optional process-start identity, token, and epoch. `execution_attempts`, keyed by `(run_id, exec_epoch)`, explicitly stores `exec_token`, phase, timestamps, owner identity, and interruption reason. It is the **single authoritative home of execution phase**; phase is not duplicated on `runs`.

Mutations split into two classes by whether they can cross an external-effect boundary. These names deliberately avoid CLAUDE.md's Category A/B/C side-effect taxonomy:

**State-only mutations** (mint, rotate, `stash`, `pop`, `release`, and any pure claim/stash/stack change). No actor and no external side effects. These are one `BEGIN IMMEDIATE` transaction: resolve, verify, guard every affected run against foreign execution ownership, write, bump the relevant versions, and commit. Project/session-scoped stack and stash operations perform their complete read-modify-write in this one transaction; they therefore need no separate session version. If a future workflow splits a session-scoped read and write across transactions, it must introduce and CAS a `session_version` rather than relying on SQLite's per-transaction serialization.

**Effectful machine mutations** (`pass`, `fail`, `complete`, `stop`, `goto`, `collect`, and `delegate`). These run an XState transition and may wait for machine effects, including shell commands that run for minutes. A SQL transaction MUST NOT be held across the actor run. One shared core entry point owns the complete protocol below; CLI, MCP, and plugin frontends invoke that typed core operation and never receive an execution token or drive individual transactions. The shared executor builds on the existing `updateWithStateReturning` shape rather than duplicating the choreography per command:

The current actors already return typed output without persisting mid-compute; `sendAndSync` performs the single authoritative persistence after effects settle. The SQLite design preserves that model. A future actor that needs intermediate durable progress must express it as an explicit machine protocol rather than writing around the shared executor and self-invalidating its captured `state_version`.

1. **Read + capture** (short transaction or snapshot read): resolve and verify the complete claim predicate, including own-run lifecycle/linkage and delegated parent existence/lifecycle/linkage, then capture the child and dependency versions needed to re-check it.
2. **Acquire execution ownership** (short `BEGIN IMMEDIATE`): install a fresh execution token and increment the run's monotonic execution epoch under the captured claim/state CAS, with phase `claimed`.
3. **Declare the effect boundary** (short `BEGIN IMMEDIATE`): immediately before invoking the actor path that may spawn or call external code, change the exact owned attempt from `claimed` to `effect_started`. This deliberately errs toward uncertainty: a crash after this marker but before the syscall requires recovery rather than an unsafe automatic retry.
4. **Compute** (NO transaction held): run the XState transition and its effects.
5. **Commit** (short `BEGIN IMMEDIATE`): re-check the complete claim predicate, including parent existence/lifecycle/linkage, classify the row through one total typed `classifyCommitRow` function, then update authoritative run state and clear execution ownership atomically —
   ```sql
   BEGIN IMMEDIATE;
   -- SELECT decides the outcome; the UPDATE's WHERE alone cannot, because
   -- 0 rows changed is ambiguous between "run gone" and "generation moved".
   SELECT r.state_version,
          r.claim_generation AS current_claim_generation,
          c.issued_generation, c.status AS claim_status,
          p.id AS parent_id, p.lifecycle AS parent_lifecycle,
          c.parent_linkage_version,
          r.exec_token, r.exec_epoch, a.phase AS exec_phase
     FROM runs r
     LEFT JOIN claims c ON c.controlled_run = r.id AND c.key = :claimKey
     LEFT JOIN runs p ON p.id = c.parent_run_id
     LEFT JOIN execution_attempts a
       ON a.run_id = r.id AND a.exec_epoch = r.exec_epoch
    WHERE r.id = :runId;
   --   no row                                  → missing
   --   no matching row for a previously captured claim,
   --   or an inactive claim/tombstone            → claim_superseded
   --   inactive claim or run-generation mismatch → claim_superseded
   --   for delegated claims only: missing/terminal parent
   --   or invalid/moved parent linkage            → claim_superseded
   --   state_version    != :capturedStateVer   → concurrent_modification
   --   execution identity mismatch              → execution_in_progress or recovery_required
   --   else:
   UPDATE execution_attempts
      SET phase = 'committed', finished_at = :finishedAt
    WHERE run_id = :runId
      AND exec_epoch = :executionEpoch
      AND exec_token = :executionToken
      AND phase = 'effect_started';
   -- Require exactly one changed attempt row before continuing.
   UPDATE runs SET <snapshot+state>,
                   state_version = state_version + 1,
                   exec_pid = NULL,
                   exec_token = NULL
     WHERE id = :runId
       AND state_version = :capturedStateVersion
       AND claim_generation = :capturedClaimGen
       AND exec_token = :executionToken
       AND exec_epoch = :executionEpoch;
   -- Both UPDATEs must change exactly one row. A SELECT-classified success
   -- followed by either 0-row UPDATE is an invariant violation: ROLLBACK and
   -- surface an internal error; never COMMIT or report `committed`.
   COMMIT;
   ```

**Transaction boundary rule.** A `BEGIN IMMEDIATE` holds SQLite's single write lock, so holding one across slow work re-creates RD-810. A transaction wraps only state mutations and cheap verification. Every external side effect—process spawn, command execution, `createDelegation`, `resolveExtraVars`, CLI/helper calls, and filesystem discovery—happens outside it. The acquire, effect-boundary marker, and final commit are separate short transactions. For `delegate`, expensive preparation is step 4; only authoritative writes are in step 5.

**The execution lease is the crux, and it must be process-aware, not time-based.** Because effects run outside the transaction, an irreversible effect can complete and then lose its coordinator before the state commit. A time-based lease would violate the repo's explicit synchronization invariant: a slow-but-live writer must not lose authority merely because it is old. The lease design:

- **Ownership token and fencing epoch are distinct.** Acquisition records `exec_pid`, a random `exec_token`, and monotonic `exec_epoch` on the active run reference while inserting the attempt's sole phase value as `claimed`. The token identifies one acquisition and prevents an old holder from releasing or committing a newer acquisition. The epoch orders attempts and may fence a downstream service only if that service receives and enforces it. Arbitrary shell commands generally do not.
- **Atomic uncontended acquisition.** Under `BEGIN IMMEDIATE`, acquisition uses a conditional top-level `UPDATE ... RETURNING exec_epoch` requiring `exec_token IS NULL`, the captured child `claim_generation` and `state_version`, an active presented claim, and—when delegated—the captured parent/linkage still existing and active. Exactly one returned row means acquired; zero rows is classified before rollback. SQLite's single writer makes this the atomic winner without `SELECT FOR UPDATE`/`SKIP LOCKED`.
- **Liveness is evaluated outside SQLite, then protected by tuple CAS.** SQLite cannot evaluate `kill(pid,0)` inside `UPDATE`; there is no `exec_pid_is_dead` SQL predicate. A contender reads the observed run owner plus joined attempt phase `(exec_pid, exec_token, exec_epoch, phase)`, ends the read transaction, probes the PID conservatively outside SQLite (`ESRCH` means dead; `EPERM` or unknown means alive), then opens `BEGIN IMMEDIATE` and changes only that exact joined identity. If another process reclaimed or reissued it meanwhile, zero rows prevents stealing the new lease. PID reuse can conservatively leak availability; use a portable process-start identity as an additional observed field if implementation probing establishes one, but never trade that false-live case for unsafe reclamation.
- **Phase-aware dead-owner recovery.** A dead owner in `claimed` is definitely pre-effect and its exact tuple may be cleared/reclaimed automatically. A dead owner in `effect_started` is ambiguous: the CLI may have died before spawn, during the command, or after the external effect completed but before commit; its child/process group may also still be running. Exact-tuple CAS first moves the attempt to `recovery_pending`, which continues to block ordinary mutations without granting execution authority. Core then sends a typed, pure `EXECUTION_OUTCOME_UNKNOWN` event through the XState machine and atomically persists the resulting recovery snapshot, increments `state_version`, records the attempt reason, and clears active ownership. A crash during recovery leaves `recovery_pending` resumable and never re-enters the original effect path.

  `recoveryRequired` is a **non-final top-level XState state** with outgoing reconciliation transitions. Persisted `Lifecycle` remains `running`; the state is open but blocked, rather than falsely `completed`/`stopped` or widened into a pseudo-terminal lifecycle. Child-to-parent projection is `{ kind: 'not_terminal', reason: 'recovery_required' }`: the parent cannot advance, and status/collection surfaces the recovery reason rather than presenting ordinary running work. Explicit reconcile/retry/stop is a typed machine transition. Automatic retry is permitted only for an enforceable idempotency contract. The direct storage-owned `lifecycle: 'stopped'` fallback in `actor-service` must migrate to a typed machine event in the same phase so crash behavior is not split between machine and storage.
- **Token-and-epoch-guarded commit and cleanup.** Successful state commit clears ownership atomically in the same transaction and requires both `exec_token` and `exec_epoch`. Refusal or exception before `effect_started` may best-effort release the exact `claimed` tuple. Any exit after `effect_started` that cannot record a known state-machine outcome must atomically record `recovery_required`; if that cleanup fails, the surviving lease row self-heals through dead-owner recovery. Cleanup uses the non-masking `await using` policy, but a disposer never blindly clears an ambiguous `effect_started` attempt.
- **Lease respect is structural and symmetric with version bumps.** The invariant is `claim-generation bump-set ⊆ lease-respect-set` and `state-version writer-set ⊆ lease-respect-set`. Claim/stash `BEFORE` triggers immediately `RAISE(ABORT)` whenever their controlled run still has active execution ownership; a trigger never waits while holding the database writer lock. The store converts that abort to typed `execution_in_progress`. Any optional bound-wait is implemented by the core caller retrying the **entire short transaction** after the lock has been released. An owner final transaction first verifies its exact token/epoch and clears the active run reference as part of the authoritative run update, then performs related claim/stash writes in the same transaction; a later failure rolls the clear and all writes back together. Every unowned `runs` update requires `exec_token IS NULL`; owner commit/recovery requires the exact token/epoch. Lease-management writes are separate exact-tuple templates. This covers mint, claim, rotate, stash/pop, release, prune, stack/session changes that advance run state, and future writers by storage shape—not an enumerated service call-site list.
- **Parent liveness is a cross-run invalidator.** Delegated claim validity depends on both child and parent. A transaction that makes parent P terminal must find every still-linked child C and immediately abort with `execution_in_progress` if any C has live execution ownership. With no conflicts, it atomically terminalizes P and updates the linked child claim/linkage rows; their structural trigger owns the child `claim_generation` bump. Core may retry the whole parent-terminal transaction outside SQLite according to the bounded-wait policy, but never waits inside a transaction. Conversely, child acquire and commit join/re-check P and the linkage. Serialization gives two safe outcomes: an already-running child finishes before P becomes terminal, or P commits first and the child's acquisition/commit is refused. Parent deletion/prune follows the same rule. The in-commit join is a mandatory backstop, not a substitute for lease-respecting cross-run invalidation.
- **Multi-run acquisition is all-or-none.** An operation that may execute against several runs acquires every deduplicated affected run in one short `BEGIN IMMEDIATE`, verifies the exact requested count and every captured version, and rolls back all acquisitions on any conflict. SQLite's one writer removes row-lock ordering deadlocks; sorting remains useful for deterministic diagnostics. Liveness probes remain outside the transaction and stale tuples are CAS-cleared before retrying the all-or-none acquisition.
- **Lease fields are DB-only operational sync state.** They never enter XState context or the persisted machine snapshot. Acquiring, moving `claimed → effect_started → recovery_pending`, and clearing a successful lease do not independently increment `state_version` or `claim_generation`. The machine transition into `recoveryRequired` is a true snapshot mutation and does increment `state_version`.

With invalidators respecting the lease, a live holder cannot have its authority invalidated mid-effect. A coordinator can still die after an effect and before the final commit; that outcome is not reconstructible and is therefore surfaced durably as `recovery_required`, never claimed as committed and never silently retried. This is the SQLite form of per-run execution serialization: one uniform PID-aware lease on the run, replacing the ad-hoc ranked file locks — but note it is retained synchronization, not eliminated synchronization (see the honest-scope note below).

The guarded write's inputs are explicit and strongly typed: branded `ClaimGeneration`, `StateVersion`, and `ExecutionEpoch` values plus `runId`, claim lookup key, execution token, and captured parent/linkage evidence. Rotated/released claims remain superseded tombstones while any active/recovery attempt can reference their issuance; later GC cannot turn an in-flight result into an unclassified SQL `NULL`. The classifier handles run-present/claim-absent explicitly as `claim_superseded`, while a genuinely absent run is `missing`; parent fields are required only for delegated claims, and `NULL` parent fields on a non-delegated claim are valid. The required discriminated union is `committed | claim_superseded | concurrent_modification | execution_in_progress | recovery_required | missing`; `classifyCommitRow` is total and exhaustively tested. A caller may apply the explicit bounded-wait policy to `execution_in_progress`, but MUST NOT wait-and-retry through `recovery_required`.

**Honest scope: SQLite dissolves the four-lock rank, but not per-run execution serialization or exactly-once effects.** The transaction + dual-CAS genuinely removes the lock rank, the ABBA traps, and the #608 check-then-act *for state writes*. It does **not** remove the need to serialize command execution per run, stop authority being invalidated mid-effect, or reconcile an effect whose coordinator died before recording its outcome. Those problems are orthogonal to storage and would exist under any backend. The execution lease provides recognized-owner serialization and stale-DB-commit fencing; `recovery_required` provides the fail-closed crash policy. Claiming the migration deletes all synchronization or guarantees exactly-once shell effects would be false.

### Every command's atomicity

- **`pass` / `fail` / `complete` / `stop` / `goto`**: effectful machine mutation—acquire, compute, and commit with complete claim/dependency CAS.
- **`delegate`** (fresh + retry): the supersede + optional child release + persist-issued-substep become one step-5 transaction — the "three separate writes, partial mutation on refusal" defect is gone by construction.
- **`collect`**: persisted completion rows already belong to the target run; draining all applicable rows and advancing that target is one leased target-run commit. If the target becomes terminal, its session release and invalidation of claims for children it controls occur in that same transaction. Reporting the now-committed terminal outcome to its own parent is a separate, idempotent parent transaction and never reopens the committed target mutation. `collect` does not lease or rewrite the completed child runs merely because their reports are consumed; any actual cross-run invalidation follows the parent-liveness rule above.
- **`abort`, `stash`, `pop`, mint/rotate/release**: state-only mutation—one guarded transaction unless the operation also drives a machine transition, in which case it uses the shared effectful executor.

## No migration

The SQLite store is a new persisted schema. Old JSON state (`session.json`, `runs/*.json`) is **not** imported — it is rejected, and the recovery path is the standard one: finish, stop, prune, or restart from source (CLAUDE.md). The DB carries its own schema version (a `schema_version` table/pragma); an incompatible version is rejected, never migrated. No legacy JSON parsing, no dual-read fallback.

## Scope and Phasing

**Proportionality — #608 stays live during the migration (a decision to ratify, not assume).** #608 is P1, but under this design it is not closed until the run/session state, completions/actor persistence, and claim commands are all on SQLite (steps 2–4). That is a long road for an urgent race. This spec deliberately accepts #608 remaining open behind the migration rather than shipping the rejected SessionLock-guard stopgap first — because that stopgap is the fragile, partial design this work exists to replace, and building it would be throwaway effort. The race requires a concurrent claim-invalidation landing inside another process's mutation window, which is uncommon in practice. **If that exposure is judged unacceptable for the interim, the alternative is to land the SessionLock-guard plan as a temporary mitigation and supersede it — an explicit tradeoff for the owner to decide.** The recommendation is to accept the interim exposure and go straight to the durable fix.

This is a persistence-layer replacement, not a call-site patch — it touches `RunbookStateManager`, `SessionService`, `actor-service`, `completion-service`, `collection-service`, `lifecycle-command-service`, and the CLI/MCP/plugin consumers that reach them (all currently insulated behind `CommandTargetReader` and the service APIs).

**No intermediate phase may ship mixed authority.** A lock and its transactional replacement guard the *same* invariant; deleting a lock before its replacement exists (or while some commands still rely on it) leaves that invariant unguarded. In particular `runGuardedParentAdvance` holds `SessionLock` across the open-child check and the decisive callback — deleting `SessionLock` before the equivalent transaction exists breaks it. Therefore the phases below are **internal implementation commits behind a single cutover**, not independently deployable releases: at no committed-and-released point is authority split across JSON and SQLite, and no lock is deleted until its transactional replacement is in place and all its dependents are converted. The whole store flips from JSON to SQLite in one release; the phases exist to make that transition reviewable, not shippable piecemeal.

Suggested internal sequence (`writing-plans` will refine):

1. **Schema + typed driver/store seam + ownership protocol.** Define branded counters, the total row classifier, narrow injectable store, explicit adapter capabilities, `claim_generation` triggers, structural writer guards, `state_version`, active owner identity, and durable single-source `execution_attempts.phase`; implement both adapters, concrete WebContainer detection, exact-tuple recovery, the shared core effectful executor, and all-or-none affected-run operations. Pin cross-run parent invalidation and the complete crash protocol before migrating behavior.
2. **Run + session state** onto the DB (runs, claims, stash, stack) behind the seam, with the SQLite-backed replacements for `RunStateLock`/`SessionLock` invariants landing in the same step they're removed.
3. **Completions + actor persistence + recovery state**: route `sendAndSync` persistence through the shared executor; add the non-final `recoveryRequired` state, typed reconciliation events, explicit parent projection, status diagnostics, and migrate the direct storage-owned stopped fallback to a machine event. Replace `CompletionLock` only behind the unshipped cutover.
4. **Claim-authorized commands**: convert `pass`/`fail`/`complete`/`stop`/`goto`/`delegate`/`abort`/`stash`/`pop` to the core entry points. Do not delete `DelegationLock` yet because `collect`/upward reporting still depends on it.
5. **`collect` and cross-run terminal propagation.** Convert target drain/advance, atomic terminal release, child-claim invalidation, and idempotent upward reporting. All four domain locks may now be removed behind the cutover once repository search proves no dependent remains.
6. **Demo integration.** Bundle sql.js into the `site/` snapshot; verify the homepage scenarios on the sql.js adapter.
7. **Cutover + cleanup.** Delete the four domain-lock modules and twins only after all dependents are converted. Keep `file-lock.ts` for artifact-manifest writes and the sql.js adapter. Rewrite both `docs/internal/architecture.md` and the root `CLAUDE.md` concurrent-write guidance to describe the transactional model, the remaining file-lock consumers, non-masking cleanup, execution ownership, and recovery handling.

Incompatible on-disk state is rejected at the cutover, never migrated.

## Testing

- **Claim-invalidation race before acquisition** (native adapter): one process invalidates the claim (stash/release/rotate) after another captures authority but before it acquires execution ownership; assert acquisition returns `claim_superseded`, no effect begins, and the run contains only the invalidator's committed change. The separate lease-respecting-invalidation test covers invalidation after acquisition.
- **Lease contention** (native adapter): two effectful machine mutations on the same run; assert only one acquires ownership and executes, while the other gets `execution_in_progress`.
- **Optimistic CAS before acquisition** (native adapter): a state-only mutation advances `state_version` after an effectful command's capture but before acquisition; assert acquisition returns `concurrent_modification` and no effect begins.
- **Invalidation respects the lease** (native adapter): while an effectful command is mid-compute, a concurrent stash/release/rotate transaction immediately gets `execution_in_progress` and does not bump `claim_generation`; after commit/release, a fresh transaction proceeds. Test any opt-in caller retry loop separately from the trigger.
- **Structural writer discipline**: enumerate every SQL write path, not service names. Any claim/stash write or run `state_version` update under a foreign token aborts in the same transaction; the exact owner commit/recovery succeeds. Mutation testing removes each guard in turn and must be killed.
- **Parent ended during child effect**: while delegated child C owns execution, attempt to complete/stop/prune parent P. The parent transaction immediately refuses and does not change P or C's generation. After C commits, a retried P transaction may become terminal; its child claim/linkage update triggers C's generation bump. The inverse race—P commits first—makes C acquisition fail before effects. The child final classifier independently rejects missing/terminal/mismatched P.
- **PID-aware reclamation, not age-based**: a held lease whose owner PID is alive is never reclaimed regardless of age; `EPERM`/unknown is treated as alive. Liveness is probed outside SQLite and cleanup conditionally changes only the exact observed `(pid, token, epoch, phase)` tuple. A delayed release/commit from attempt A changes zero rows after attempt B acquires.
- **Crash-boundary fault injection**: kill the owner (a) before acquisition commit, (b) after `claimed` but before `effect_started`, (c) after `effect_started` before spawn, (d) while the child runs, (e) after a fake external effect but before final commit, and (f) after the atomic state-commit/ownership-clear transaction. Cases (a) and (b) are automatically re-executable; (c)–(e) become `recovery_required`; (f) observes both committed state and cleared ownership—never one without the other.
- **Surviving child/process group**: kill the coordinator while its child remains alive; assert no automatic re-execution occurs and explicit recovery exposes the possible overlap. Where process-tree supervision is supported, assert retry remains blocked until the tree is dead unless the operator explicitly overrides after reconciliation.
- **Effect ambiguity proof**: use an unfenced fake external sink to demonstrate that automatic retry could duplicate an effect even though the old token cannot commit DB state. This pins the boundary between DB fencing and external-effect semantics.
- **Phase and version semantics**: acquiring, marking `effect_started`/`recovery_pending`, and successful atomic clear do not independently move `state_version`; the pure machine transition to `recovery_required` does. Kill the recovery worker after `recovery_pending`; assert a successor resumes `EXECUTION_OUTCOME_UNKNOWN` without invoking the original command. Every execution acquisition increments `exec_epoch`, and neither token nor epoch is reused.
- **All-or-none multi-run acquisition**: race overlapping sets `{A,B}` and `{B,C}`; exactly one set acquires and the loser owns nothing. Duplicate or missing requested IDs fail the exact-count check and commit no partial acquisition.
- **Outcome taxonomy unit tests**: the discriminated `committed | claim_superseded | concurrent_modification | execution_in_progress | recovery_required | missing` is exhaustive; a rotated claim resolves `claim_superseded` (tombstone), a truly absent one `missing`, and an ambiguous dead attempt cannot be treated as ordinary contention or auto-retried.
- **Commit invariant**: force either final UPDATE to affect zero rows after the classifier selected success; assert rollback and an internal invariant error, never `committed`.
- **Recovery machine shape**: `recoveryRequired` is non-final, persists with lifecycle `running`, blocks ordinary execution, projects to the parent as open-with-recovery-required, and accepts only typed reconciliation transitions.
- **`collect` / `delegate` atomicity**: an invalidation mid-workflow leaves the run entirely unchanged — the defects the JSON design could not prevent.
- **sql.js durability and lock scope**: simulate termination around export, file `fsync`, rename, and directory `fsync`; assert the acknowledged-write contract and orphan cleanup. Assert the adapter lock is released between acquire/effect/commit transactions, recursive adapter use cannot self-deadlock, and a second writer either observes the persisted lease or fails closed.
- **Adapter parity (functional, not concurrency-semantic)**: the same SQL suite runs green on both adapters. This proves single-threaded behavioral equivalence only — it does **not** prove `sql.js` is safe under the multi-process conditions the native adapter handles. "Same SQL, same schema" is not "same guarantees": the native adapter serializes across processes; `sql.js` requires there be exactly one writer. The single-writer enforcement (stale-check fail-closed) is tested separately.
- **Checked-in WebContainer substrate probe**: the empirical findings (native `node:sqlite` stubbed, WASM runs, `sql.js` works and persists across sequential processes) are load-bearing — they justify "SQLite everywhere." They MUST be a committed, reproducible Playwright test (a test-only isolated page, not a shipped route), so that a WebContainer runtime change re-validates the substrate choice cheaply instead of silently invalidating it. Prose findings in this spec are the record; the test is the guard.
- **WebContainer smoke**: the `site/` homepage scenarios (`run`/`pass`/`fail`/`goto`) pass with the sql.js adapter and bundled snapshot (extend the existing Playwright suite).
- **No-secret-leak**: refusal envelopes route through `redactClaimId`; the bearer secret never appears in output.
- **Mutation/property coverage** (scoped Stryker) on the dual-CAS predicate and the version-bump sites.

## Risks and Open Items

- **Recovery UX and idempotency contracts**: the safety policy is settled—ambiguous effects become `recovery_required` and are not automatically rerun—but the operator-facing inspect/reconcile/retry command and any future declaration of enforceable idempotency still require implementation design. A mere author assertion that a shell command is idempotent is not enforcement; automatic retry requires an effect-specific contract the runtime can actually apply.
- **Contention wait policy and operator UX**: database transactions and triggers always refuse immediately; they never wait while holding SQLite's writer lock. The default command behavior is therefore an immediate typed `execution_in_progress` response identifying the affected run. Step 1 may add an explicit opt-in caller-level wait mode, but must choose and test a finite total budget, retry backoff, cancellation behavior, and progress diagnostics. A short budget can time out routine parent stop/complete while a child runs; an unbounded budget makes those commands appear hung and is forbidden. The retry loop releases the DB lock between attempts and never retries `recovery_required`.
- **Process identity and supervision portability**: PID liveness is available on the real multi-process hosts, but PID reuse may conservatively leak availability and child processes may outlive the CLI. Step 1 must probe whether a portable process-start identity and process-tree supervision are available on each supported host. Failure to provide them never permits age-based or optimistic reclamation; it falls back to fail-closed recovery.
- **Operator recovery from false-live PID identity**: a reused PID can conservatively wedge ownership forever. Recovery UX must include an explicit, audited force-reconcile operation that displays the recorded PID/start identity and effect-ambiguity warning, transitions through the machine, and never silently re-executes the effect.
- **`node:sqlite` is experimental**: it ships behind an `ExperimentalWarning` through Node 22/23 and its API is still stabilizing (the probe emitted that warning). The production native path depends on a not-yet-stable built-in. Fallback stance: the native adapter is a thin driver boundary, so if the `node:sqlite` API shifts, the real-machine adapter can swap to `better-sqlite3` (a native addon, viable on real machines — only WebContainer bars addons, and WebContainer uses sql.js regardless). Track Node's SQLite stabilization.
- **Blob location and sql.js write cost are one coupled decision, not two**: the `sql.js` adapter re-serializes the *whole* DB on every write, so if the XState `snapshot` lives in-DB, a large snapshot makes every WebContainer write O(snapshot). Resolve together in step 1: keep the `snapshot` inline only while it stays small (true for the demo); if any sql.js target carries large snapshots, move the `snapshot` to a content-addressed FS blob (written before commit, DB holds the ref, orphans pruned) so exports stay cheap. In-DB remains the default for correctness simplicity on the native path; the FS-blob escape is named, not deferred vaguely.
- **sql.js snapshot bundling**: sql.js (JS + `.wasm`) must be bundled into the WebContainer snapshot at build time (the demo avoids runtime `npm install`). Build-step change, mechanical.
- **Global write serialization vs per-run parallelism**: today `RunStateLock` is per-run, so writes to different runs proceed in parallel; one SQLite DB in WAL gives concurrent readers but a single writer, so all state writes across all runs serialize on one writer lock. Fine for the expected handful of short transactions; a deliberate tradeoff to note for wide fan-out runbooks (many concurrent delegated children writing). If it ever bites, the escape is per-run or sharded databases — out of scope here.
- **Scale**: large migration; the single-cutover phasing and the no-migration rule (break active runs, don't migrate) keep each step bounded and keep authority un-split.

## Rejected Alternatives

- **SessionLock-outer guard** — fragile, partial, defers the hard paths (see 2026-07-17 plan).
- **Collapse onto per-run `RunStateLock`** — reentrancy timeout + rank inversion + cross-run parent dependency.
- **Fencing-token over JSON files** — hand-rolled transactions; four criticals (cross-file non-atomicity, no-migration violation, non-atomic `delegate`/`collect`). SQLite provides the transaction natively and (via sql.js) runs everywhere, so the JSON substrate buys nothing.
- **Lock manager / conservative 2PL over the files** — a valid deadlock-free-by-construction option, but it keeps the file substrate and its crash-consistency burden; SQLite subsumes it.
- **Automatic dead-owner reclaim and re-execution** — valid only as an explicit at-least-once policy for enforceably idempotent effects. Rejected as Rundown's default because a command may have completed externally before its coordinator died, or an orphan child may still be running; a replacement execution could duplicate or overlap an irreversible effect.
- **Time-expiring/heartbeat execution lease** — common in distributed queues and leader election, but it can replace a paused-yet-live holder. Rejected for arbitrary, unbounded local commands unless the protected downstream resource enforces the monotonic epoch; Rundown's default remains process-aware and fail closed.
- **A generic in-memory JS store for WebContainer** — unnecessary once sql.js is confirmed working; keeps one SQL schema instead of a second persistence model.
